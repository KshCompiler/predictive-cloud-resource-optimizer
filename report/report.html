1Summary

What the project is

Cloud servers get sudden spikes of users. Normal auto-scaling waits until the server is already overloaded, then starts a new server — which takes 60–90 seconds to be ready. Users feel the slowdown during that time.

Our system uses an LSTM (a neural network for time-based data) to predict the load 5 minutes ahead. If a spike is coming, servers are started early. At the end we will compare proactive (prediction-based) and reactive (normal) scaling on: how fast capacity is ready, how much capacity is wasted, and how many false alarms happen.

4Step 1.2 — Getting and cleaning the data

4.1 The dataset

Bitbrains was a Dutch company that hosted servers for banks and insurance companies. TU Delft published real readings from 1,250 of these servers (the fastStorage set), one reading every 5 minutes. Each server is one CSV file with 11 columns. We keep what we need and make 4 columns:

{{SVG:columns}}

Why CPU, memory and network together? When a job starts, all three usually rise together. Seeing all three gives the model more clues than CPU alone. Why memory as a percentage? Raw memory is in millions of KB while CPU is 0–100; without converting, memory would look more important just because its numbers are bigger.

4.2 Choosing a VM (utils/explore.py)

Most servers are almost idle. A model trained on an idle server just learns to say "about 2%" and learns nothing about spikes. So we checked all 1,250 files.

{{IMG:plots/fig_vm_landscape.png}}

Three rules:

  1. At least 2,000 readings (about 7 days) → 1,177 VMs.
  2. Average CPU between 20% and 60% (not idle, not always full) → 158 VMs.
  3. Sort by standard deviation, highest first (the CPU that moves most).
  4. Check that all three parts move — training, validation and test. A VM that goes idle for its last days would be tested on a flat line, which proves nothing.
  5. Memory and network must not be dead. The model predicts all three metrics, so a metric stuck on one value would be a column with nothing to learn. A metric is rejected if it never changes, or if one value covers more than 90% of its readings. → caught 12 VMs with dead memory and 225 with dead network across the dataset.

→ 20 rejected by these last checks, leaving 138 real candidates, led by VM 270.

{{SVG:funnel}}

Fix made during the work: the plan said to check only the first 100–200 files. But file names sort as text (1, 10, 100, 1000, 11…), so that is not a fair sample — it found zero good VMs. Checking all files found 158 and took about a minute.

5Step 1.3 — Preparing the data for the model

File: utils/preprocessing.py. It turns the clean table into batches the LSTM can train on. The order of the steps is very important.

{{SVG:preprocess}}

A. Split by time (70% / 15% / 15%)

First 70% of the time for training, next 15% for validation, last 15% for testing. Never random: the model must learn from the past and be tested on the future, like in real life.

{{IMG:plots/fig_split.png}}

B. Scale to 0–1 using training data only

The scaler learns the min and max from the training part only, then applies them to all three parts. If it also looked at the test part, test information would leak into training and the results would look better than they really are.

{{SVG:leakage}}

Proof it worked: training data scales to exactly 0.00–1.00, but test data reaches 1.91. That can only happen if the scaler never saw the test data. The scaler is saved to models/scaler.joblib for the dashboard.

C. Make windows: 60 readings in, 1 reading out

Each example is 60 readings (5 hours) of CPU, memory and network; the answer is the next reading (5 minutes later). Windows are made inside each part separately, so no example mixes training and test data.

6Problems found and next steps

Fixed 1. The survey was counting days when a VM was switched off

When a VM is switched off, the datacenter still writes a row every 5 minutes with every number at 0. The survey counted those as "0% busy", which dragged averages down. The first choice, VM 214, looked like mean 44.21% only because its last 4.6 days were switched off; while running it averaged 68.43%, above our 60% limit. All six of the original top VMs had the same problem and none of them actually qualified.

Fix applied: explore.py now skips rows where the memory given to the VM is 0. Checked first on a 32-file sample: in every such row, all the other numbers are 0 too.

Fixed 2. The survey never checked the test period

After fix 1 the new winner was VM 200 — highest std of all, never switched off. But its last 4.5 days are flat zero, and that is exactly the slice kept back for testing. Training would have run fine and the final score would have meant nothing.

Fix applied: a fourth rule. The survey now measures the three parts the way preprocessing splits them and rejects any VM where one part does not move. That removed 20 more VMs, leaving 138 candidates, and VM 270 is the top one.

Still open. The top candidates are near-copies

VMs 270, 249, 263, 247, 285 and 279 behave almost the same (probably one job spread over many machines), so choosing between them changes little. Ranking by std also favours on/off machines, because switching between 0% and 100% gives the largest possible std. VM 270 is still bimodal at the 5-minute level: 47% of readings at 0–2% and 36% above 98%. It does, however, have a clear daily rhythm (29% at 11:00, 62% at 20:00), which the earlier choice lacked.
